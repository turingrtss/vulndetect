\begin{abstract}
We train simple TF-IDF classifiers on a publicly available code vulnerability dataset and achieve 84.7\% binary classification accuracy. However, feature analysis reveals that the model partially learns from natural language descriptions embedded in code comments rather than from vulnerable code patterns. The top predictive features include substrings of the words ``vulnerable'' and ``safe'' appearing in comments and variable names. This label leakage inflates reported accuracy and calls into question benchmarks built on similar datasets. We document the full experimental setup, results, and implications for ML-based vulnerability detection research.
\end{abstract}

\section{Introduction}

Machine learning approaches to vulnerability detection have gained significant attention, with multiple papers reporting high accuracy on benchmark datasets \cite{diversevul,securityeval}. These results suggest that ML models can learn to distinguish vulnerable code from safe code with useful precision.

We investigate whether a simple baseline model---TF-IDF vectorization with logistic regression---can achieve competitive results on a publicly available dataset, and more importantly, \textit{what} the model actually learns. Our findings suggest that high accuracy numbers on code vulnerability datasets should be interpreted cautiously.

\section{Experimental Setup}

\subsection{Hardware}
All experiments were conducted on a constrained environment:
\begin{itemize}
  \item CPU: ARM64 (Oracle Cloud, 2 cores, Neoverse-N1)
  \item RAM: 12 GB
  \item GPU: None
  \item OS: Ubuntu 22.04
\end{itemize}

This deliberately constrained setup demonstrates that meaningful ML experiments do not require expensive GPU infrastructure.

\subsection{Models}
We evaluate three classifiers on TF-IDF character n-gram features (3--6 character windows, 50,000 max features, sublinear TF scaling):

\begin{enumerate}
  \item \textbf{Logistic Regression} ($C=1.0$, max 1000 iterations)
  \item \textbf{Random Forest} (100 estimators)
  \item \textbf{Gradient Boosting} (100 estimators)
\end{enumerate}

All experiments use an 80/20 train/test split with stratification. We report accuracy, precision, recall, F1-score for the vulnerable class, and false positive rate.

\subsection{Interpretation}

The model's strongest vulnerability indicators are substrings of the word \textit{vulnerable} (\texttt{vuln}, \texttt{vul}, \texttt{uln}). Its strongest safety indicators are substrings of \textit{safe} and \textit{secure}. These words appear in code comments, variable names, and docstrings within the dataset samples.

This constitutes \textbf{label leakage}: the classification labels are partially encoded in the input features through natural language descriptions. The model achieves high accuracy partly by detecting these descriptions rather than learning actual code vulnerability patterns.

Only one genuinely code-related feature appears in the top 10 vulnerability indicators: \texttt{eval(}, which corresponds to the use of Python's \texttt{eval()} function---a well-known dangerous pattern.

\subsection{Implications}

\begin{enumerate}
  \item \textbf{Reported accuracy is inflated.} The 84.7\% accuracy partly reflects the model's ability to read comments, not detect vulnerabilities.
  \item \textbf{The model will fail on real code.} Production code does not contain comments labeling itself as ``vulnerable.''
  \item \textbf{Other studies using similar datasets may have the same problem.} Any model trained on code samples with descriptive comments risks learning the descriptions instead of the patterns.
  \item \textbf{Dataset construction matters.} Code vulnerability datasets should strip comments and normalize variable names before use, or the benchmark is measuring the wrong thing.
\end{enumerate}

\section{Proposed Fixes}

To build a model that learns actual vulnerability patterns:

\begin{enumerate}
  \item \textbf{Strip comments and docstrings} before training. Force the model to learn from code structure only.
  \item \textbf{Normalize identifiers.} Replace variable names with generic tokens (\texttt{var\_1}, \texttt{func\_2}) to prevent the model from learning naming conventions.
  \item \textbf{Use CVE fix commits.} Paired before/after code from real vulnerability fixes provides naturally clean labels without descriptive comments.
  \item \textbf{Re-evaluate accuracy} after stripping. The true model capability is the residual accuracy after removing label leakage.
\end{enumerate}

We intend to implement these fixes and report updated results in a follow-up study.

\begin{itemize}
